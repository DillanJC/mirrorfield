# Plan C: Gate-in-Agent-Loop Integration (Road A final step)

## In plain language

We have already proven, with careful statistics, one real thing: while a language model writes an answer, the hesitation in its own word choices (how torn it was between words) predicts whether that answer is wrong — as long as we compare each answer's hesitation against the model's *recent answers of the same kind of work*. What we have NOT yet built is the thing Dillan actually wants: a working system where the model answers questions and a "gate" checks each answer *before it is shown*, then either presents it, presents it with a warning, or holds it back. This plan builds that — a live demo on Dillan's own PC where you watch questions stream by and see the gate hold back the shaky answers — plus an honest measurement of whether the gate actually helps. "Helps" means: when the gate holds back its least-confident answers (around 20% of them), it must catch meaningfully more mistakes than holding back *the same share* of answers at random would. That last part matters: we compare against random-at-whatever-fraction-the-gate-actually-held-back, never against a fixed 20%, so the gate cannot make its own test easier by holding back more answers than planned. We set the exact numbers below, before running anything. Success looks like: the answers that get through are measurably more accurate than the model's overall accuracy, with statistics that clear our pre-set bars. Failure looks like: the gate's choices are no better than random — which would still be valuable, because it would mean the lab-validated signal does not survive the trip into a real running system, and we would know exactly where the loss happened (the saved data lets us check every stage). This is engineering on top of the one result that survived all our falsification attempts, so it is the highest-probability direction we have — but the measurement still has to be done honestly, because demos are where wishful thinking hides.

## Why this matters / what it builds on

This is the final step of Road A and the first end-to-end realization of Dillan's original goal: **stop likely-bad outputs before they are sent.**

The prior is the strongest in the project. Every ingredient is already validated and locked (WORK_MAP.md §4b–4i, ORIENTATION.md §2):

- The lean log-prob gate (token margin + entropy + boundary ratio) predicts wrong outputs at per-task AUC 0.60–0.74 on Qwen2.5-3B, CIs clear 0.5, improves with scale.
- Cross-task it works at 0.63 [0.58, 0.69] using an unsupervised rolling z-score; it transfers to unseen task types (QNLI 0.72, RTE 0.63).
- Hard constraint: rolling buffers must hold same-context traffic (mixed streams → chance). This constraint is already engineered into the shipped tool as the per-context `RollingGate` (`context_id` parameter).
- The shipped MCP server (`C:\Users\User\mirrorfield\mirrorfield\mcp\server.py`) already emits calibrated `p_correct` and `p_correct_relative`.

What's missing is only the loop: model → answer → gate → decision → (show / warn / withhold), and a measurement of *gate value* (selective prediction), which is a different question from "does the score rank errors" (already answered offline). An AUC of 0.63 is modest; whether it translates into a *useful* abstention policy at a real operating point is exactly what this plan measures — honestly, because a positive here is the project's first user-visible safety artifact, and an inflated one would repeat the project's worst pattern.

Honesty about the prior: ~80% that the offline AUC reproduces live (same model, same prompts, fresh items); maybe 65–70% that the selective-prediction lift clears its pre-registered bar at the chosen operating point (the gate is modest, and accuracy-among-presented deltas are noisy even at the enlarged sample sizes below).

## The plan, step by step

All new files go in `C:\Users\User\mirrorfield\experiments\` (repo convention). Every script gets the standard header: fixed `SEED=42`, dry-run default, `--run` to execute. Generation is greedy (`do_sample=False`) so model outputs are deterministic; only *stream order* is seed-varied where stated.

**Step 1 — Build the gated agent (`experiments\gate_agent.py`).** CPU + brief GPU smoke. ~1 session.
- `LocalLM` class: wraps Qwen2.5-3B-Instruct exactly as `calibrate_gate.generate()` does (fp16 on CUDA, chat template, greedy, `MAX_NEW=24`, top-5 logprobs per step → list of `{token_id: logprob}` dicts). 3B fp16 ≈ 6.2 GB, fits the 8 GB 3060 Ti (already proven by the calibration run).
- `GateClient` abstraction with two interchangeable implementations:
  - `InProcessGate`: imports `compute_token_margins/entropies/boundary_ratio`, `calibrated_p_correct`, and instantiates `RollingGate(window=50, min_history=5)` directly from `mirrorfield.mcp.uncertainty` — the *same shipped code*, no copies. **It rounds the three features to 4 decimals before scoring/buffering, exactly mirroring server.py lines 301–303**, so the in-process path is numerically identical to the served path.
  - `McpGate`: persistent stdio session to `python -m mirrorfield.mcp.server` (cwd = `C:\Users\User\mirrorfield`), calling the real `confidence_report` tool with `tokens`-aligned `top_logprobs` and `context_id`. Fixes the old layer's hardcoded-args bug; parses the *leaned* schema.
- `GatedAgent.answer(question, context_id) -> {answer_text, p_correct_relative, p_correct_calibrated, confidence_score, warming_up, decision}` where `decision ∈ {PRESENT, VERIFY, ABSTAIN}` comes from the pre-registered policy (Step 2). During warmup (`buffer < 5`): decision is always VERIFY.
- **Parity test** (in-file, `--parity`): 20 synthetic + 5 real generations through both gate paths (fresh RollingGate state on both sides); assert **exact equality of the 4-decimal `p_correct_relative` values AND identical decisions on all 25 items** (both paths round identically, so exact match is the correct expectation — a float tolerance would mask schema/plumbing bugs). Artifact: console pass/fail + `gate_agent_parity.json`.
- Wall-clock: build ~1 session; smoke/parity runs < 10 min GPU.

**Step 2 — Pre-register thresholds and criteria (`experiments\derive_gate_thresholds.py`).** Pure CPU, seconds. MUST complete and be committed BEFORE any Step 4 generation.
- Load `calibrate_gate_rows.npz` (training-era data — using it for thresholds leaks nothing into the fresh eval). Round features to 4 decimals (matching the live path), then for each task stream run rows through a fresh `RollingGate` to get the distribution of `p_correct_relative` values. **Stream order for this threshold pass = per-task `RandomState(42)` permutation (matching `validate_rolling_gate.py`); the order seed is recorded in `gate_thresholds.json`** — RollingGate scores are order-dependent, so an unpinned order would make the thresholds irreproducible.
- Derive and freeze, **from post-warmup RTE+QNLI scores only (SST-2 excluded — it is not in the scored eval population, and including it would target the wrong population mix):** `tau_abstain` = 20th percentile of the pooled RTE+QNLI scores (target ≈ 20% abstention), `tau_present` = 50th percentile (VERIFY band between them). As a stability check, also compute and report the tau values under order seeds 43 and 44; **the seed-42 values are the frozen thresholds.**
- Write `experiments\gate_thresholds.json` containing the thresholds, the order seed, the stability-check values, AND the full pre-registered success/failure criteria text (the section below, verbatim).
- Artifact: `gate_thresholds.json`, committed to git with the criteria, before any eval data exists.

**Step 3 — Build the evaluation harness (`experiments\eval_gate_value.py`).** Same session as Step 2.
- **Calibration-index exclusion (do exactly this — the naive version silently contaminates):** reproduce the calibration's index lists by replaying `calibrate_gate.load_task` (imported, not copied) with **ONE shared `np.random.RandomState(42)` in the exact original task order — rte, then qnli, then sst2, n=250 each. The shared RNG state across the three calls is load-bearing**: each shuffle advances it, so a per-task fresh `RandomState(42)` reproduces only RTE's indices and would leak up to 250 calibration items (whose features the exported logreg/isotonic was FIT on) invisibly into the "fresh" QNLI set. Assert each exclusion set has exactly 250 unique indices and is disjoint from the selected fresh indices. Fresh RTE needs no exclusion (calibration used the validation split; fresh items come from train).
- Fresh item selection (frozen, seed 123): **RTE: 450 from the train split. QNLI: 500 from validation minus calibration indices.** SST-2: 150 from validation minus calibration indices (included for ecological realism of the multi-context stream; pre-declared NOT scoreable — too few errors at ~91% accuracy, per WORK_MAP §4h/4i). Optional stretch: MRPC 200 from validation with a frozen new prompt ("Sentence 1 / Sentence 2 / Do these two sentences mean the same thing? Answer yes or no first, then a brief reason."; label 1 = yes) — a live unseen-task-type transfer test. Prompts for RTE/QNLI/SST-2: byte-identical to `calibrate_gate.TASKS`.
- Generation pass (the only big GPU step): each item answered once by `LocalLM` via `GatedAgent` with `InProcessGate`, per-task `context_id`, items streamed in seed-123 order within task. Save EVERYTHING per item to `eval_gate_value_rows.npz`: features (margin/entropy/boundary), answer text, parsed prediction, parse-success flag, correct (0/1) vs gold (`_first_of` convention, identical to calibration: unparseable = wrong), task, stream position, **and the selected dataset indices** (so exclusion/contamination is auditable forever). ~1,100 core generations × ~2–4 s ≈ 60–120 min wall-clock on the 3060 Ti (+~10–15 min if MRPC is included).
- Analysis passes (pure CPU on the saved rows, seconds each — no regeneration ever):
  a. Per-context scoring: fresh `RollingGate` per task, exclude first 20 items per context (matches §4i WARMUP), compute pooled RTE+QNLI AUC of `p_correct_relative` vs wrong, bootstrap CI (N=2000), **and per-task AUCs + CIs (co-registered — they arbitrate the abandon rule, see criteria).**
  b. Selective prediction at the frozen `tau_abstain`: **realized abstention rate** (the fraction actually withheld — reported always, and used in every comparison; the nominal 20% target is never used as a null), error-recall among abstained, accuracy among presented vs overall, risk–coverage curve (risk = error rate among presented, sweep coverage 50–100%). Bootstrap unit: resample the post-warmup scored items with replacement, recomputing error-recall AND realized abstention rate within each resample (threshold stays fixed).
  c. Mixed-stream negative control: re-score the SAME rows through ONE shared `context_id` over a seed-interleaved all-task stream; AUC + CI.
  d. Shuffled-label null: 10 permutations of the correct/wrong labels against the real scores; record mean/max AUC.
  e. Order replication: repeat (a) with stream orders from seeds 43 and 44 (scores depend on buffer history; generations don't change).
  f. MRPC (if run): own context, own AUC + CI + 5 shuffled nulls — secondary endpoint.
  g. **Sensitivity row (co-reported, not gating):** P1 AUC and P2 recall recomputed *excluding* unparseable-answer items, plus the unparseable count per task. Unparseable answers are labeled "wrong" (kept identical to calibration), but rambling outputs tend to have low margins, so the gate may catch them "for the wrong reason" — if the headline survives only with unparseable items included, the write-up must say so explicitly.
- Artifacts: `eval_gate_value_rows.npz`, `eval_gate_value_results.json`, `risk_coverage.png` (curve with the pre-registered operating point marked and the "random abstention" diagonal for reference).

**Step 4 — Run the evaluation.** 1 session: GPU generation pass + CPU analyses + verdict against the pre-registered criteria. If P1 fails (below), run the prescribed single debugging pass: re-score `calibrate_gate_rows.npz` through the identical analysis code — if THAT still shows 0.63, the discrepancy is in the fresh data path (prompt drift, parser, item mix); document and proceed per the per-task disambiguation and abandon rules in the criteria.

**Step 5 — The watchable demo (`experiments\run_gate_demo.py`).** 1 session; GPU ~10 min per run.

## Pre-registered success / failure criteria

Frozen now; copied verbatim into `gate_thresholds.json` in Step 2 before any run. Primary population: fresh RTE+QNLI items, post-warmup (first 20 per context excluded), per-context buffers, score = `p_correct_relative`. Bootstrap = 2,000 resamples of the post-warmup scored items, with replacement, all derived quantities recomputed per resample.

Plain-language keys, defined once and used throughout: **AUC** (a ranking score: 0.5 = the gate orders right and wrong answers no better than a coin flip, 1.0 = perfectly); **CI lower bound** (the cautious end of the statistical uncertainty range — even the pessimistic reading must clear the bar); **error-recall** (of all the mistakes the model made, the fraction the gate held back); **realized abstention rate** (the fraction of answers the gate actually held back on the fresh data — which can drift from the 20% design target, so it is measured, never assumed).

- **P1 (signal survives the live path):** pooled RTE+QNLI wrong-output AUC ≥ 0.58 AND 95% bootstrap CI lower bound > 0.50. (Locked offline band: 0.63 [0.58, 0.69]; the 0.58 floor allows fresh-data noise.) Per-task AUCs + CIs are co-registered for the disambiguation rule below.
- **P2 (the gate demonstrably helps — the headline claim):** at the frozen `tau_abstain`, the 95% bootstrap CI of **(error-recall among abstained − realized abstention rate)** has lower bound > 0, with both quantities recomputed inside every bootstrap resample (threshold fixed). Why the difference and not a fixed 0.20 bar: a random gate's error-recall equals whatever fraction it abstains, so if fresh scores drift and the gate abstains 30%, random catches 30% — a fixed 0.20 null would let a literally random gate pass. Comparing recall to the *realized* rate makes the null exactly zero no matter how the score distribution shifts; the gate cannot set the difficulty of its own bar. Co-reported, not gating: (i) rank-based descriptive check — abstain exactly the bottom 20% of post-warmup items by `p_correct_relative` (label-blind), recall vs the exact 0.20 null; (ii) accuracy among presented minus overall accuracy, with CI; (iii) the realized abstention rate itself.
- **S1 (secondary, stretch):** MRPC (never seen by calibration) AUC 95% CI lower bound > 0.50 → live replication of unseen-task transfer. Failing S1 does not fail the plan; it bounds the transfer claim.
- **"The gate abstains randomly" verdict:** P1 passes but P2's CI (the recall-minus-realized-rate difference) includes 0 → we may publish the AUC and the risk–coverage curve, but the demo ships labeled "modest gate — ranking signal real, operating-point value not demonstrated," and the phrase "the gate helps" is NOT used anywhere.
- **Per-task disambiguation (fires before any abandon talk):** fresh RTE comes from the train split — a known sourcing shift; fresh QNLI comes from validation, the same distribution as the locked result. If pooled P1 fails but **QNLI-alone has CI lower bound > 0.50**, the verdict is "RTE-train-arm shift — foundation intact, transfer claim bounded," documented as such; the foundation-in-question rule does NOT fire on that pattern.
- **Abandon this direction if:** pooled P1 fails AND **QNLI-alone also fails** (its CI includes 0.50) AND the Step 4 debugging pass confirms the analysis code reproduces 0.63 on the saved calibration rows AND one focused bug-hunt session finds no implementation error. That combination means the validated signal does not transfer to fresh same-distribution traffic — the foundation itself is in question, which is bigger news than the demo and must be written up as such. No threshold tuning, no metric swapping, no second operating point after seeing data.

## Controls & verification

- **Negative control 1 (mixed-stream):** scoring the same answers through one shared context buffer must degrade: shared-buffer pooled AUC at least 0.05 below the per-context AUC, expected ≈ chance (replicates §4i test 3 through the live pipeline). If it does NOT degrade, our central deployment constraint is misunderstood — investigate before any claims.
- **Negative control 2 (shuffled labels):** 10 label permutations; mean AUC in [0.45, 0.55], max < 0.58.
- **Seeds:** generation greedy + `torch.manual_seed(42)` (no sampling anywhere — the §4e unseeded-sampler trap is structurally impossible here); item selection seed 123; calibration-exclusion replay = one shared `RandomState(42)` in original task order; threshold-pass and stream-order seeds 42/43/44.
- **Replication:** P1 must hold (CI clears 0.50) for all 3 stream orders, with AUC spread < 0.06. The demo itself is run at least twice end-to-end to confirm identical decisions (determinism check).
- **Parity check:** in-process gate vs real MCP server agree *exactly* (4-decimal `p_correct_relative`, identical decisions) on 25 items — both paths round features to 4 decimals per server.py lines 301–303 — so the eval measures exactly what the demo ships.
- **Circularity check — what target does the method get to define? None.** The label is "did the answer match the GLUE gold label," fixed by dataset authors years before this project; the gate never touches it. Thresholds come from pre-existing calibration rows, frozen and committed before the eval data exists. The P2 null is pinned to the *realized* abstention rate, so the gate's behavior on fresh data cannot loosen its own bar (the one place the draft plan had left that door open). Prompts are frozen copies of the calibration prompts. The one researcher degree of freedom left — curating demo questions — is explicitly quarantined: demo output carries no numbers; all numbers come from the pre-registered harness.

## Honest risks

- **P(null on P1): ~15–20%.** Largest confound: fresh RTE items come from the *train* split (validation exhausted by calibration) — a mild distribution shift, now explicitly disambiguated in the criteria so it cannot masquerade as a foundation failure; and Qwen pretraining contamination of GLUE applies equally to calibration and eval, so it does not differentially bias the comparison but does inflate absolute accuracy.
- **P(P2 fails given P1 passes): ~30–35%.** Power math from the project's own calibration error rates (RTE 44/250 = 17.6% wrong, QNLI 57/250 = 22.8% wrong): with 450 RTE + 500 QNLI fresh items, ≈910 scored post-warmup, expected errors ≈ 0.176×430 + 0.228×480 ≈ **185**. At ~185 errors, recall SE ≈ 0.033; a plausible true recall of ~0.30–0.33 at AUC 0.63 against a realized abstention rate near 0.20 is a difference of ~0.10–0.13 ≈ 2.5–3.5σ — adequately powered, where the draft's smaller design (≈113 expected errors, not the mistakenly claimed ~190) would have been close to a coin flip. A weak run lands in the "modest gate" verdict, which is survivable but not the headline Dillan hopes for.
- **Most likely way this wastes a week:** the MCP stdio client on Windows (async context teardown, anyio cancel scopes — the old agent layer's cleanup code hints at this pain). Mitigation is structural: the eval never depends on the stdio path (in-process gate, same shipped code, parity-proven), so plumbing pain can only delay the *demo polish*, never the science.
- **Quieter risks:** answer-parsing (`_first_of`) labels unparseable answers as "wrong" — kept deliberately identical to calibration, with the dedicated sensitivity analysis (Step 3g) quantifying how much of the headline rests on them; the silent-contamination trap in index replay (now spelled out with an assertion, and the chosen indices are saved to the npz for permanent auditability); VRAM pressure if anything else is using the GPU during the 60–120 min pass (run with nothing else open); the temptation, if P2 barely misses, to nudge `tau_abstain` after the fact — forbidden above, and the risk–coverage curve already shows every operating point honestly.
